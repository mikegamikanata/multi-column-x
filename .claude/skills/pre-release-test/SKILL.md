# リリース前試験 (pre-release-test)

リリースのたびに、`docs/release/pre-release-checklist.md`（以下「チェックリスト」）の項目で試験を実施し、**試験項目とその結果をリリースPRの本文に記載する**。
`version-release` の Phase 5（リリースPR作成）の後、Phase 6（マージ）の前に実行する。単独で実行してもよい。

途中で打ち切って「次は何をしますか」と尋ねない。ただし各ステップの確認ゲートは必ず待つ。

## 原則（必ず守る）

- **チェックリストは「常に確認する項目」の一覧であり、結果を書く場所ではない。**
  - チェックリストに書いてよいのは、項目の追加・削除・内容（観点・手順・期待結果など）の修正だけ
  - 結果・実施日・実施回数（「第 2 回」など）・対象バージョン・実施記録は**チェックリストに書かない**。すべてリリースPRに書く
- **結果の記録先はリリースPR（develop → main、タイトル `v<version>`）の本文**。PRごとに 1 回分の試験記録になる
- **項目の No. は再採番しない**。削除した項目の No. は欠番にし、再利用しない（過去のリリースPRの結果表が No. で項目を参照しているため）。新規項目は各プレフィックスの最大番号の次を使う
- 安全ルール（X への外部影響操作の禁止、OS 設定変更の禁止、データ・端末設定の退避と復元）は `autonomous-manual-test` に従う

## 前提

- `gh` CLI が認証済みであること（ローカル開発環境専用。`gh` が使えない環境では着手前にその旨をユーザーに伝える）
- 実機操作（Windows の CDP / Android エミュレータ）の手順・スクリプトは `.claude/skills/autonomous-manual-test/`（`SKILL.md` / `reference.md` / `scripts/`）を使う

## 手順

### Step 1: リリースPRと比較範囲を確定する

1. リリースPRを特定する: `$ARGUMENTS` に番号があればそれを使う。無ければ `gh pr list --base main --head develop --state open` で探す。見つからなければ、リリースPRを作ってから実行するようユーザーに伝えて止まる
2. 前回のリリースタグを確定する: `git tag --sort=-v:refname | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$' | head -1`（`v0.8.6-temp-1` のような一時タグは除外する）
3. 比較範囲 `<前回タグ>..origin/develop` を確定し、試験するコミット（`git rev-parse --short origin/develop`）を記録する

### Step 2: チェックリストの項目を過不足なく揃える（項目の増減のみ）

1. `<前回タグ>..origin/develop` でマージされた PR を洗い出す: `git log <前回タグ>..origin/develop --merges --oneline` と `gh pr view <番号> --json title,body,files`
2. PR ごとに、チェックリストに対応する項目があるかを確認する。機能追加・挙動変更・バグ修正の PR で、リリース前に実アプリで確認すべき観点が無ければ項目を追加する（各機能 PR でチェックリストに追加済みのはずだが、漏れをここで補う）
   - 項目の書き方はチェックリストの既存行に合わせる（No. / 由来PR / カテゴリ / 観点 / 事前条件 / 操作手順 / 期待結果 / 優先度 / 実施者）
   - 期待結果は「どうなれば OK か」が第三者に判定できる書き方にする
   - 削除された機能の項目は削除する（No. は欠番）。仕様変更で手順・期待結果が古くなった項目は修正する
3. 追加・削除・修正の案を一覧にしてユーザーに提示し、**承認を得てから**チェックリストを編集する（確認ゲート）
4. チェックリストの変更は、develop から作業ブランチ（例: `docs/pre-release-checklist-v<version>`）を切ってコミットし、develop 向け PR にする。リリースPRへ取り込むかは、ユーザーに確認する（取り込む場合は先にその PR をマージしてからリリースPRを更新する）
   - このコミット・PR に**結果を含めない**。項目の増減と修正だけにする
   - 変更が無ければこの手順は飛ばす

### Step 3: 自動チェック（X-xx）を実施する

チェックリスト「自動チェック」節のコマンドを順に実行し、合格基準で判定する（`check-creation` スキルの内容と重なるものはそれを使ってよい）。

- 実行は機械的な作業のため `model: haiku` のサブエージェントに委譲してよい（判定の根拠となる件数・エラー内容を報告させる）
- 署名鍵が無いなどローカルで実施できないものは `OK（一部）` または `対象外` とし、理由を備考に書く

### Step 4: 実機の試験を実施する

1. 項目を振り分ける
   - 実施者が「自動試験可」の項目 → エージェントが実施する
   - 「人」「人（外部影響あり）」の項目、Linux の項目 → 結果を `人が実施` にして、Step 6 の残項目に載せる
2. 自動試験可の項目を `autonomous-manual-test` の手順（退避 → ビルド → 起動 → 操作と検証 → 後片付け）と安全ルールで実施する
   - 実機操作は判断を伴うため `model: sonnet` のサブエージェントに委譲する。委譲前に「メイン=<モデル名> / サブエージェント=<モデル名>」を出力する
   - 委譲プロンプトには、チェックリストの絶対パスと実施対象の No.、ビルドするコミット、結果ファイルのパス、スクラッチのパス、Android の serial、`autonomous-manual-test` の安全ルールを読む指示を必ず入れる
   - サブエージェントには**チェックリストを編集させない**。結果はスクラッチ（リポジトリ外）か `tmp/release-test/v<version>/results.md`（gitignore 済み）に `No. | 結果 | 備考` 形式で書かせる
3. 期待結果と異なる事象を見つけても、その場でコードを直さない。`NG` または `NG（要判断）` として記録し、ユーザーに報告する

### Step 5: 結果の判定と書式

結果欄はチェックリストの凡例（未実施 / OK / OK（一部） / NG（要判断） / NG / 対象外 / 人が実施）だけを使う。

- 共通回帰（C-xx）は `W: OK / A: OK（一部）` のようにプラットフォーム別に書く
- 根拠の無い OK を書かない（DOM・設定値・ファイルサイズ等の客観的な根拠を備考に 1 つ以上）
- `OK（一部）` は未確認の範囲を、`対象外` は理由を、`NG` は事象・再現手順を備考に書く
- NG とは断定できない気付きは「要確認事項」に回す

### Step 6: リリースPRの本文に記載する

`references/pr-body-template.md` の書式で本文を作り、`gh pr edit <PR番号> --body-file <ファイル>` で更新する。

- 本文はスクラッチか `tmp/release-test/v<version>/pr-body.md` に作る（コミットしない）
- **試験項目は全件を載せる**（結果が `人が実施` や `未実施` の項目も省略しない）。項目の内容は `No.` と観点の要約で示し、手順・期待結果はチェックリストへのリンク（試験したコミットのパーマリンク）で参照させる
- **GitHub の PR 本文は 65,536 文字が上限**。超える場合は、本文に実施条件・サマリ・要確認事項・残項目を残し、節ごとの結果表を PR コメント（`gh pr comment <PR番号> --body-file`）に分けて投稿し、本文からそのコメントへのリンクを張る
- 人が後から結果を埋めたら、同じ書式のまま本文（またはコメント）の該当行を更新する。試験をやり直した場合も、チェックリストではなくリリースPRを更新する
- 更新後に `gh pr view <PR番号> --json body -q .body | head -40` で反映を確認する

### Step 7: 報告とリリース可否の確認

ユーザーに次を報告し、**リリース可否の判断を仰ぐ**（エージェントが「リリース可」と決めない）。

- 件数サマリ（OK / OK（一部） / NG（要判断） / NG / 未実施 / 人が実施 / 対象外）
- NG・NG（要判断）の内容
- 要確認事項
- 人が実施すべき残項目
- チェックリストを更新した場合はその PR

判断の結果（リリース可 / 不可、残項目をどう扱うか）は、リリースPR本文の「判定」欄に書く。

## 完了条件

- チェックリストの項目が前回リリース以降の変更に対して過不足ない（変更した場合は結果を含まない PR になっている）
- リリースPRの本文（または本文からリンクされたコメント）に、チェックリストの全項目とその結果、実施条件、サマリ、要確認事項、人の残項目が載っている
- 後片付け（アプリのデータ・端末設定の復元）が済んでいる
- リリース可否をユーザーに確認した

## 禁止事項

- チェックリストに結果・実施日・実施回数・対象バージョンなどの記録を書くこと
- 項目の No. を再採番すること、欠番を再利用すること
- 試験していない項目に OK を書くこと、項目をリリースPRの結果表から省くこと
- チェックリストの項目追加・削除をユーザー承認なしに行うこと
- エージェントの判断だけでリリース可と判定すること
- `autonomous-manual-test` の安全ルールで「実施しない」とされた操作を行うこと
